PART 1 · 경계Bounded Context

경계의 기준은 기술 계층이 아니라 도메인이다

  • DDD의 Bounded Context = 모델이 일관되게 통하는 범위
  • 같은 단어도 컨텍스트마다 의미가 다름
  • 자를 곳: 모델의 의미가 바뀌는 지점
접수 컨텍스트의 "예약"
방문 시각대기 순번
진료 항목환자 정보
결제 컨텍스트의 "예약"
결제 수단청구 금액
환불 규정정산 상태
같은 "예약" — 컨텍스트가 다르면 속성과 규칙이 다르다
PART 1 · 경계경계 판정 기준

경계는 데이터 소유권과 변경 주체로 판정한다

  • 이 데이터를 쓰기(write)하는 주체가 누구인가
  • 이 로직이 바뀔 때 누가 바꾸는가
  • 함께 바뀌는 것끼리 묶고, 따로 바뀌는 것을 나눔 (변경의 응집)
Q1. 이 데이터의 write 주체는?
↓
Q2. 이 로직의 변경 주체는?
↓
같은 주체 → 같은 서비스로 응집
읽기는 여럿이어도, 쓰기 주인은 하나
PART 1 · 경계경계의 크기

너무 잘게 자르면 분산 시스템 비용만 남는다

  • 서비스 하나 추가 = 네트워크 경계·배포 파이프라인·모니터링 추가
  • 마이크로가 목적이 아님: 팀이 감당 가능한 단위가 상한
  • 애매하면 크게 시작해서 나중에 자르는 편이 되돌리기 쉬움
효용 곡선이 꺾이는 지점 너머는 비용만 는다
PART 2 · 통신동기 호출

동기 호출은 편리한 만큼 결합을 만든다

  • REST/gRPC: 구현 단순, 즉시 응답 필요할 때 적합
  • 대가: 가용성 결합 — 상대가 죽으면 나도 실패
  • 호출 체인이 길어질수록 전체 가용성은 곱셈으로 하락
svc A99.9%
→
svc B99.9%
→
svc C99.9%
0.999 × 0.999 × 0.999 ≈ 99.7%
체인 전체 가용성 = 각 구간 가용성의 곱
PART 2 · 통신Timeout · Retry · Circuit Breaker

동기 호출에는 반드시 방어 장치를 붙인다

  • Timeout: 무한 대기 차단, 스레드/커넥션 고갈 방지
  • Retry: 멱등한 요청에만, 지수 백오프 + 지터
  • Circuit Breaker: 연속 실패 시 차단하고 fallback으로 전환
Circuit Breaker 상태 전이
PART 2 · 통신이벤트 기반 통신

비동기 이벤트는 시간적 결합을 끊는다

  • 발행자는 수신자의 존재·상태를 몰라도 됨
  • 수신자 장애 시에도 발행 성공 — 메시지는 브로커에 적재
  • 대가: 결과적 일관성(eventual consistency), 흐름 추적 난이도 상승

PART 2 · 통신메시지 전달 보장

at-least-once가 현실적 기본값이라
멱등성이 필수다

  • exactly-once는 브로커·컨슈머·저장소 전 구간 보장이 어려움
  • 현실적 선택: at-least-once (유실 없음, 중복 허용)
  • 컨슈머는 중복 소비를 전제로 멱등하게 설계
보장 수준유실중복실무
at-most-once있음없음유실 허용 로그 등
at-least-once없음있음기본값 + 멱등 컨슈머
exactly-once없음없음전 구간 보장 어려움

PART 2 · 통신비동기 운영

컨슈머 lag은 비동기 시스템의
핵심 관측 지표다

  • lag = 발행 속도와 소비 속도의 차이 누적
  • lag 증가 = 처리 지연이 사용자 경험으로 전파되는 전조
  • 파티션 설계·컨슈머 스케일링이 처리량의 상한 결정
PART 3 · 데이터일관성 문제

서비스를 나누는 순간

  • 한 비즈니스 동작이 여러 서비스의 쓰기를 요구
  • 2PC(2단계 커밋): 가용성·성능 비용으로 실무에서 기피
  • 대안: 로컬 트랜잭션의 연쇄 + 보상 = Saga

PART 3 · 데이터Transactional Outbox

"DB 커밋과 이벤트 발행"의 원자성은
Outbox로 푼다

  • 문제: DB 커밋 성공 + 브로커 발행 실패 = 유실

PART 3 · 데이터동시성 제어

분산 락은 최후의 수단 —
설계로 피하는 게 먼저다

  • 우선순위: 유니크 제약 → 조건부 업데이트 → 분산 락
  • Redlock 등 분산 락: 락 만료·경합·시계 오차 등 고려 사항 많음
  • 락을 쓰면 락 실패 시나리오까지 설계에 포함

1st DB 유니크 제약

가장 단순·견고. DB가 원자성을 보장

2nd 조건부 업데이트

상태 조건을 걸어 원자적 전이만 허용

last 분산 락 (Redlock 등)

만료·경합·시계 오차 관리 필요 — 락 자체가 장애 지점이 될 수 있음

PART 4 · DB 분리왜 마지막 관문인가

DB를 나누지 않으면 MSA는 완성되지 않는다

  • 공유 DB = 스키마가 암묵적 공용 API
  • 인덱스·슬로우 쿼리·커넥션 풀을 전 서비스가 공유하는 성능 결합
  • 서비스 분리의 마지막 관문이자 가장 되돌리기 어려운 작업

스키마 결합

필드 하나 바꾸는 데 전 서비스 협의

성능 결합

한 서비스의 슬로우 쿼리가 전체 레이턴시로

장애 결합

커넥션 풀 고갈·장애가 전 서비스에 전파

PART 4 · DB 분리분리 단계 설계

DB 분리는 3단계 —
접근 분리, schema 분리, 물리 분리

STEP 1 접근 분리

타 도메인 직접 조회 제거,
소유 도메인 API 경유

끊는 결합 — 접근 결합

STEP 2 schema 분리

같은 클러스터 내
도메인별 DB(schema)로 이동

끊는 결합 — 스키마 결합

STEP 3 물리 분리

클러스터 자체 분리
비용 대비 효과 따져 선택

끊는 결합 — 성능·장애 결합

2단계까지만으로도 스키마 결합과 접근 결합은 끊긴다 — 3단계는 필수가 아니다
