PART 1 · 경계Bounded Context

경계의 기준은 기술 계층이 아니라 도메인이다

  • DDD의 Bounded Context = 모델이 일관되게 통하는 범위
  • 같은 단어도 컨텍스트마다 의미가 다름
  • 자를 곳: 모델의 의미가 바뀌는 지점
접수 컨텍스트의 "예약"
방문 시각대기 순번
진료 항목환자 정보
결제 컨텍스트의 "예약"
결제 수단청구 금액
환불 규정정산 상태
같은 "예약" — 컨텍스트가 다르면 속성과 규칙이 다르다
경계를 어디서 자를 것인가. 답은 기술 계층이 아니라 도메인입니다. DDD의 Bounded Context 개념이 유용합니다. 같은 "예약"이라는 단어도 접수 컨텍스트와 결제 컨텍스트에서 필요한 속성과 규칙이 다릅니다. 모델의 의미가 바뀌는 그 지점이 서비스를 자를 지점입니다.
PART 1 · 경계경계 판정 기준

경계는 데이터 소유권과 변경 주체로 판정한다

  • 이 데이터를 쓰기(write)하는 주체가 누구인가
  • 이 로직이 바뀔 때 누가 바꾸는가
  • 함께 바뀌는 것끼리 묶고, 따로 바뀌는 것을 나눔 (변경의 응집)
Q1. 이 데이터의 write 주체는?
↓
Q2. 이 로직의 변경 주체는?
↓
같은 주체 → 같은 서비스로 응집
읽기는 여럿이어도, 쓰기 주인은 하나
이론은 Bounded Context인데, 실무에서 판정할 때 유용한 질문은 두 가지입니다. 이 데이터에 쓰기를 하는 주체가 누구인가, 이 로직이 바뀔 때 누가 바꾸는가. 함께 바뀌는 것끼리 묶는 게 원칙입니다. 읽기는 여러 서비스가 할 수 있어도 쓰기 주인은 하나여야 합니다.
PART 1 · 경계경계의 크기

너무 잘게 자르면 분산 시스템 비용만 남는다

  • 서비스 하나 추가 = 네트워크 경계·배포 파이프라인·모니터링 추가
  • 마이크로가 목적이 아님: 팀이 감당 가능한 단위가 상한
  • 애매하면 크게 시작해서 나중에 자르는 편이 되돌리기 쉬움
효용 곡선이 꺾이는 지점 너머는 비용만 는다
반대 방향의 함정도 있습니다. 너무 잘게 자르는 겁니다. 서비스가 하나 늘 때마다 네트워크 경계, 파이프라인, 모니터링 대상이 같이 늡니다. 합치는 것보다 자르는 게 쉽기 때문에, 애매하면 크게 시작해서 필요할 때 자르는 쪽이 안전합니다.
PART 2 · 통신동기 호출

동기 호출은 편리한 만큼 결합을 만든다

  • REST/gRPC: 구현 단순, 즉시 응답 필요할 때 적합
  • 대가: 가용성 결합 — 상대가 죽으면 나도 실패
  • 호출 체인이 길어질수록 전체 가용성은 곱셈으로 하락
svc A99.9%
→
svc B99.9%
→
svc C99.9%
0.999 × 0.999 × 0.999 ≈ 99.7%
체인 전체 가용성 = 각 구간 가용성의 곱
통신 파트입니다. 동기 호출, REST나 gRPC는 구현이 단순하고 즉시 응답이 필요한 조회에 적합합니다. 문제는 가용성 결합입니다. 상대 서비스가 죽으면 내 요청도 실패합니다. 가용성 99.9%짜리 서비스 세 개가 체인으로 엮이면 전체는 99.7%로 떨어집니다. 체인이 길수록 곱셈으로 나빠집니다.
PART 2 · 통신Timeout · Retry · Circuit Breaker

동기 호출에는 반드시 방어 장치를 붙인다

  • Timeout: 무한 대기 차단, 스레드/커넥션 고갈 방지
  • Retry: 멱등한 요청에만, 지수 백오프 + 지터
  • Circuit Breaker: 연속 실패 시 차단하고 fallback으로 전환
Circuit Breaker 상태 전이
동기 호출을 쓴다면 방어 장치는 선택이 아닙니다. 타임아웃 없는 호출은 커넥션 고갈로 이어지고 재시도는 멱등한 요청에만 백오프를 걸어서 해야 합니다. 재시도 폭풍이 장애를 키우는 경우가 많습니다. 서킷 브레이커는 연속 실패 시 아예 차단해서 죽어가는 서비스에 부하를 더 얹지 않게 해줍니다.
PART 2 · 통신이벤트 기반 통신

비동기 이벤트는 시간적 결합을 끊는다

  • 발행자는 수신자의 존재·상태를 몰라도 됨
  • 수신자 장애 시에도 발행 성공 — 메시지는 브로커에 적재
  • 대가: 결과적 일관성(eventual consistency), 흐름 추적 난이도 상승
동기 — 시간 결합
A
→
B (down)
B가 죽으면 A의 요청도 실패
비동기 — 시간 분리
A
→
Broker
⇢

B가 죽어도 발행 성공, 복구 후 소비
비동기 이벤트는 시간적 결합을 끊습니다. 발행하는 쪽은 누가 받는지, 지금 받을 수 있는 상태인지 몰라도 됩니다. 수신자가 죽어 있어도 메시지는 브로커에 쌓였다가 복구 후 처리됩니다. 대신 데이터는 결과적으로만 일관되고 흐름 추적이 어려워지는 비용을 치릅니다.
PART 2 · 통신메시지 전달 보장

at-least-once가 현실적 기본값이라
멱등성이 필수다

  • exactly-once는 브로커·컨슈머·저장소 전 구간 보장이 어려움
  • 현실적 선택: at-least-once (유실 없음, 중복 허용)
  • 컨슈머는 중복 소비를 전제로 멱등하게 설계
보장 수준유실중복실무
at-most-once있음없음유실 허용 로그 등
at-least-once없음있음기본값 + 멱등 컨슈머
exactly-once없음없음전 구간 보장 어려움
메시지 전달 보장 얘기를 안 할 수 없습니다. exactly-once는 브로커부터 저장소까지 전 구간에서 보장돼야 해서 현실적으로 얻기 어렵습니다. 실무 기본값은 at-least-once입니다. 유실은 없지만 중복이 옵니다. 그래서 컨슈머의 멱등 설계가 필수입니다. 이건 옵션이 아니라 전제 조건입니다.
PART 2 · 통신멱등 컨슈머 패턴

멱등성은 유니크 키·조건부 업데이트·
처리 이력으로 구현한다

유니크 제약

이벤트 ID·자연 키에 unique index → 중복 삽입을 DB 레벨에서 차단

조건부 업데이트

상태 기계 기반 — 유효한 전이만 허용
PENDING→PAID (O)
PAID→PAID (skip)

처리 이력

처리한 이벤트 ID 기록 → 중복 도착 시 스킵

공통 목표 — "같은 메시지가 두 번 와도 결과가 같다"
멱등 구현은 크게 세 갈래입니다. 이벤트 ID에 유니크 제약을 걸어 중복 삽입을 DB 레벨에서 막거나, 상태 기계 기반으로 유효한 전이만 허용하는 조건부 업데이트를 쓰거나, 처리한 이벤트 ID를 기록해두고 중복이면 스킵하는 방식입니다. 어느 쪽이든 "같은 메시지가 두 번 와도 결과가 같다"를 보장하면 됩니다.
PART 2 · 통신비동기 운영

컨슈머 lag은 비동기 시스템의
핵심 관측 지표다

  • lag = 발행 속도와 소비 속도의 차이 누적
  • lag 증가 = 처리 지연이 사용자 경험으로 전파되는 전조
  • 파티션 설계·컨슈머 스케일링이 처리량의 상한 결정
비동기로 넘어가면 봐야 할 지표가 바뀝니다. 핵심은 컨슈머 lag입니다. 발행 속도를 소비가 못 따라가면 lag이 쌓이고 이게 곧 사용자에게 지연으로 도착합니다. lag 알람은 필수입니다. 처리량 상한은 결국 파티션 설계와 컨슈머 스케일링이 결정합니다.
PART 3 · 데이터일관성 문제

서비스를 나누는 순간
분산 트랜잭션 문제가 시작된다

  • 한 비즈니스 동작이 여러 서비스의 쓰기를 요구
  • 2PC(2단계 커밋): 가용성·성능 비용으로 실무에서 기피
  • 대안: 로컬 트랜잭션의 연쇄 + 보상 = Saga
주문 생성commit ✓
→
결제 승인commit ✓
→
재고 차감실패 ✗
이미 커밋된 주문·결제는? — 하나의 트랜잭션으로 묶을 수 없다
데이터 파트입니다. 모놀리식에서는 트랜잭션 하나로 끝나던 일이, 서비스를 나누면 여러 DB에 걸친 쓰기가 됩니다. 2단계 커밋은 이론상 가능하지만 코디네이터가 병목이자 단일 장애점이 돼서 실무에선 거의 안 씁니다. 현실적 대안이 로컬 트랜잭션을 연쇄하고 실패 시 보상하는 Saga입니다.
PART 3 · 데이터Saga 패턴

Saga는 롤백 대신
보상 트랜잭션으로 되돌린다

  • 각 단계는 로컬 트랜잭션으로 커밋
  • 중간 실패 시 이미 커밋된 단계를 보상 트랜잭션으로 취소
  • Choreography(이벤트 연쇄) vs Orchestration(중앙 조정자)
FORWARD
T1 주문
→
T2 결제
→
T3 재고 ✗
COMPENSATE (역순)
C1 주문 취소
←
C2 결제 취소
←
T3 실패 지점
Saga의 핵심은 롤백이 아니라 보상입니다. 각 단계는 각자 DB에 커밋하고 중간에 실패하면 이미 커밋된 단계들을 취소하는 보상 트랜잭션을 역순으로 실행합니다. 구현은 두 갈래입니다. 이벤트로 자율적으로 이어지는 Choreography와 중앙 조정자가 지휘하는 Orchestration이 있습니다. 단계가 3개를 넘어가면 흐름이 보이는 Orchestration이 관리하기 쉬웠습니다.
PART 3 · 데이터Transactional Outbox

"DB 커밋과 이벤트 발행"의 원자성은
Outbox로 푼다

  • 문제: DB 커밋 성공 + 브로커 발행 실패 = 유실

멱등 컨슈머
발행이 at-least-once가 되므로 멱등 컨슈머와 세트
비동기 아키텍처의 고전적 함정 하나. DB에는 커밋됐는데 이벤트 발행이 실패하면 두 시스템이 어긋납니다. Outbox 패턴은 이벤트를 비즈니스 데이터와 같은 트랜잭션으로 outbox 테이블에 기록하고 별도 릴레이가 그걸 읽어 브로커에 발행합니다. 발행 자체가 at-least-once가 되니 앞서 말한 멱등 컨슈머와 세트로 갑니다.
PART 3 · 데이터조회 전용 복제 / CQRS

조회 결합은 데이터 복제로 끊는다

  • 쓰기 주인은 원 소유 도메인, 복제본은 읽기 전용

PART 3 · 데이터동시성 제어

분산 락은 최후의 수단 —
설계로 피하는 게 먼저다

  • 우선순위: 유니크 제약 → 조건부 업데이트 → 분산 락
  • Redlock 등 분산 락: 락 만료·경합·시계 오차 등 고려 사항 많음
  • 락을 쓰면 락 실패 시나리오까지 설계에 포함

1st DB 유니크 제약

가장 단순·견고. DB가 원자성을 보장

2nd 조건부 업데이트

상태 조건을 걸어 원자적 전이만 허용

last 분산 락 (Redlock 등)

만료·경합·시계 오차 관리 필요 — 락 자체가 장애 지점이 될 수 있음

서비스가 나뉘면 동시성 제어도 분산 문제가 됩니다. 바로 분산 락으로 가기 전에, DB 유니크 제약이나 조건부 업데이트로 풀리는지 먼저 보는 걸 권합니다. Redlock 같은 분산 락은 만료 시간, 경합, 시계 오차까지 고려할 게 많고 락 획득 실패 시나리오를 설계 안 하면 락이 또 다른 장애 지점이 됩니다.
PART 4 · DB 분리왜 마지막 관문인가

DB를 나누지 않으면 MSA는 완성되지 않는다

  • 공유 DB = 스키마가 암묵적 공용 API
  • 인덱스·슬로우 쿼리·커넥션 풀을 전 서비스가 공유하는 성능 결합
  • 서비스 분리의 마지막 관문이자 가장 되돌리기 어려운 작업

스키마 결합

필드 하나 바꾸는 데 전 서비스 협의

성능 결합

한 서비스의 슬로우 쿼리가 전체 레이턴시로

장애 결합

커넥션 풀 고갈·장애가 전 서비스에 전파

마지막 파트, DB 분리입니다. 코드를 아무리 잘 나눠도 DB를 공유하면 스키마가 암묵적인 공용 API로 남습니다. 한 서비스의 슬로우 쿼리가 전 서비스 성능에 영향을 주고요. 그래서 DB 분리가 MSA의 마지막 관문입니다. 동시에 가장 되돌리기 어려운 작업이라 순서와 안전장치가 중요합니다.
PART 4 · DB 분리분리 단계 설계

DB 분리는 3단계 —
접근 분리, schema 분리, 물리 분리

STEP 1 접근 분리

타 도메인 직접 조회 제거,
소유 도메인 API 경유

끊는 결합 — 접근 결합

STEP 2 schema 분리

같은 클러스터 내
도메인별 DB(schema)로 이동

끊는 결합 — 스키마 결합

STEP 3 물리 분리

클러스터 자체 분리
비용 대비 효과 따져 선택

끊는 결합 — 성능·장애 결합

2단계까지만으로도 스키마 결합과 접근 결합은 끊긴다 — 3단계는 필수가 아니다
DB 분리를 한 방에 하려면 실패합니다. 3단계로 나누는 게 안전합니다. 먼저 코드 레벨에서 타 도메인 직접 조회를 없애고(접근 분리), 같은 클러스터 안에서 도메인별 DB로 나눈 뒤(schema 분리), 마지막으로 클러스터를 물리적으로 분리합니다. 각 단계가 끊는 결합이 다르고 물리 분리는 비용이 커서 반드시 해야 하는 건 아닙니다. 2단계까지만으로도 스키마 결합과 접근 결합은 끊깁니다.

CASE STUDY전환 설계

컷오버는 lag이 0에 수렴해야 전환한다

  • ① full sync 완료 → ② incremental sync로 lag 수렴 확인
  • ③ 애플리케이션 커넥션을 신규 DB로 전환 (컷오버)
  • ④ 이상 시 커넥션 원복 — 롤백 경로 사전 확보
절차는 이렇습니다. full sync가 끝나면 incremental sync가 따라붙습니다. 여기서 replication lag이 0 근처로 수렴하는지 봅니다. 수렴을 확인한 뒤에 애플리케이션 커넥션을 신규 DB로 전환합니다. 중요한 건 롤백 경로입니다. 전환 후 이상이 보이면 커넥션을 원복하면 되도록, 되돌리는 절차를 먼저 정의하고 들어갔습니다.
