MSA의 핵심 속성은 독립 배포, 독립 장애 격리, 독립 스케일링 세 가지고 이 중 기준은 독립 배포입니다. 서버 개수나 레포 개수는 본질이 아닙니다. 지금 이 서비스를 배포하는 데 옆 팀과 협의가 필요하다면 서버가 열 개라도 모놀리식입니다. 화면 왼쪽처럼 서버만 나뉘고 DB를 공유하는 구조가 정확히 그 상태입니다.
PART 1 · 경계안티패턴

가장 흔한 실패는 분산 모놀리식이다

  • 서버는 나눴지만 DB를 공유: 스키마 변경이 전 서비스에 전파
  • 동기 호출 체인: 한 서비스 장애가 연쇄 장애로
  • 배포 순서 의존: 릴리즈 트레인 부활

01 공유 DB

스키마 = 암묵적 공용 API. 한 팀의 변경이 전 서비스로 전파

02 동기 호출 체인

A → B → C 체인 어디가 죽어도 전체 실패

03 배포 순서 의존

"B 먼저 배포하고 A 배포" — 독립 배포 상실

가장 흔한 실패가 분산 모놀리식이고, 결합이 남는 지점은 화면의 세 가지입니다. DB를 공유하면 스키마 변경이 전 서비스로 전파되고 동기 호출이 체인으로 엮이면 한 서비스 장애가 연쇄 장애가 되고 배포 순서가 정해져 있으면 릴리즈 트레인이 부활합니다. 이런 게 생기는 이유는 대부분 전환을 중간에 멈추기 때문입니다. 코드 나누기까지는 하는데 DB와 호출 정리가 안 된 상태죠. 오늘 다룰 기술은 전부 이 결합을 끊는 도구입니다.

경계의 기준은 기술 계층이 아니라 도메인입니다. DDD의 Bounded Context, 즉 모델이 일관되게 통하는 범위가 단위가 됩니다. 화면처럼 같은 예약이라는 단어도 접수 컨텍스트에서는 방문 시각과 순번이고 결제 컨텍스트에서는 금액과 환불 규정입니다. 이 둘을 한 모델로 합치면 필드 수십 개짜리 만능 모델이 되고 변경할 때마다 양쪽이 흔들립니다. 모델의 의미가 바뀌는 지점이 자를 자리입니다.
PART 1 · 경계경계 판정 기준

경계는 데이터 소유권과 변경 주체로 판정한다

  • 이 데이터를 쓰기(write)하는 주체가 누구인가
  • 이 로직이 바뀔 때 누가 바꾸는가
  • 함께 바뀌는 것끼리 묶고, 따로 바뀌는 것을 나눔 (변경의 응집)
Q1. 이 데이터의 write 주체는?
↓
Q2. 이 로직의 변경 주체는?
↓
같은 주체 → 같은 서비스로 응집
읽기는 여럿이어도, 쓰기 주인은 하나
실무에서 판정할 때는 두 질문을 씁니다. 이 데이터에 쓰기를 하는 주체가 누구냐, 이 로직이 바뀔 때 누가 바꾸냐. 같은 답이 나오는 것끼리 묶는 게 변경의 응집입니다. 덧붙이면 읽기는 여러 서비스가 공유해도 괜찮습니다. 하지만 한 컬렉션에 쓰기 주체가 둘이면 경계를 다시 봐야 한다는 신호입니다.
PART 1 · 경계경계의 크기

너무 잘게 자르면 분산 시스템 비용만 남는다

  • 서비스 하나 추가 = 네트워크 경계·배포 파이프라인·모니터링 추가
  • 마이크로가 목적이 아님: 팀이 감당 가능한 단위가 상한
  • 애매하면 크게 시작해서 나중에 자르는 편이 되돌리기 쉬움
효용 곡선이 꺾이는 지점 너머는 비용만 는다
반대 함정도 있습니다. 서비스가 하나 늘 때마다 네트워크 경계, 배포 파이프라인, 모니터링 대상이 같이 늡니다. 마이크로가 목적이 아니라 팀이 감당 가능한 단위가 상한입니다. 그리고 잘못 자른 걸 합치는 리팩토링이 자르는 리팩토링보다 훨씬 어렵기 때문에, 애매하면 크게 시작해서 필요할 때 자르는 쪽이 되돌리기 쉽습니다.

PART 2 · 통신동기 호출

동기 호출은 편리한 만큼 결합을 만든다

  • REST/gRPC: 구현 단순, 즉시 응답 필요할 때 적합
  • 대가: 가용성 결합 — 상대가 죽으면 나도 실패
  • 호출 체인이 길어질수록 전체 가용성은 곱셈으로 하락
svc A99.9%
→
svc B99.9%
→
svc C99.9%
0.999 × 0.999 × 0.999 ≈ 99.7%
체인 전체 가용성 = 각 구간 가용성의 곱
참고 — REST vs gRPC REST 리소스 중심(URL+JSON) · 텍스트 · 브라우저·외부 API 범용  /  gRPC 원격 함수 호출(.proto 계약) · protobuf 바이너리 + HTTP/2 · 내부 핫패스
통신 파트입니다. REST나 gRPC 같은 동기 호출은 구현이 단순하고 즉시 응답이 필요한 조회에 맞습니다. 대가는 가용성 결합입니다. 상대가 죽으면 나도 실패하니까 체인 전체 가용성이 곱셈이 됩니다. 화면 계산처럼 99.9% 셋이 엮이면 99.7%인데, 퍼센트로는 작아 보여도 허용 다운타임이 세 배가 되는 겁니다. 체인이 길수록 빠르게 나빠집니다.
PART 2 · 통신Timeout · Retry · Circuit Breaker

동기 호출에는 반드시 방어 장치를 붙인다

  • Timeout: 무한 대기 차단, 스레드/커넥션 고갈 방지
  • Retry: 멱등한 요청에만, 지수 백오프 + 지터
  • Circuit Breaker: 연속 실패 시 차단하고 fallback으로 전환
Circuit Breaker 상태 전이
참고 — 지수 백오프 · 지터 백오프 재시도 간격을 1s→2s→4s 두 배씩 늘려 상대에게 회복 시간 확보  /  지터 간격에 랜덤을 섞어 동시 실패한 클라이언트들이 같은 시각에 몰려오는 재시도 파도를 분산
그래서 동기 호출에는 방어 장치 세 개가 세트입니다. 타임아웃은 무한 대기와 커넥션 고갈을 막고 재시도는 멱등한 요청에만 지수 백오프와 지터를 걸고 서킷 브레이커는 연속 실패 시 회로를 열어 차단합니다. 재시도에 조건이 많은 이유가 있습니다. 장애 상황에서 재시도는 부하를 곱해서 죽어가는 서비스의 복구를 막는 재시도 폭풍이 되기 쉽거든요. 화면의 상태 전이도처럼 브레이커가 열렸다가 half-open으로 시험해 보고 닫히는 흐름입니다.
PART 2 · 통신이벤트 기반 통신

비동기 이벤트는 시간적 결합을 끊는다

  • 발행자는 수신자의 존재·상태를 몰라도 됨
  • 수신자 장애 시에도 발행 성공 — 메시지는 브로커에 적재
  • 대가: 결과적 일관성(eventual consistency), 흐름 추적 난이도 상승
동기 — 시간 결합
A
→
B (down)
B가 죽으면 A의 요청도 실패
비동기 — 시간 분리
A
→
Broker
⇢

B가 죽어도 발행 성공, 복구 후 소비
비동기 이벤트는 시간적 결합을 끊습니다. 발행자는 수신자의 존재나 상태를 몰라도 되고 수신자가 죽어 있어도 발행은 성공합니다. 메시지가 브로커에 쌓였다가 복구 후 처리되니까요. 대가도 화면에 있는 두 가지입니다. 데이터는 결과적으로만 일관되고 이 요청이 지금 어디까지 갔는지 추적하기가 어려워집니다. 그래서 많은 팀이 결국 correlation ID 같은 추적 체계를 따로 만들게 됩니다.
PART 2 · 통신메시지 전달 보장

at-least-once가 현실적 기본값이라
멱등성이 필수다

  • exactly-once는 브로커·컨슈머·저장소 전 구간 보장이 어려움
  • 현실적 선택: at-least-once (유실 없음, 중복 허용)
  • 컨슈머는 중복 소비를 전제로 멱등하게 설계
보장 수준유실중복실무
at-most-once있음없음유실 허용 로그 등
at-least-once없음있음기본값 + 멱등 컨슈머
exactly-once없음없음전 구간 보장 어려움
전달 보장은 표의 세 단계입니다. at-most-once는 유실을 감수하는 거라 대부분 도메인에서 선택지가 아니고 exactly-once는 이상적이지만 얻기 어렵습니다. 왜 어렵냐면, 컨슈머가 처리를 끝내고 ack를 보내기 직전에 죽으면 브로커는 처리 여부를 알 수 없어서 다시 보낼 수밖에 없거든요. 그래서 실무 기본값은 at-least-once, 유실은 없지만 중복은 온다입니다. 결론은 컨슈머를 중복 전제로 짜야 한다는 겁니다.

공통 목표 — "같은 메시지가 두 번 와도 결과가 같다"
그 멱등 구현이 화면의 세 갈래입니다. 이벤트 ID에 유니크 제약을 걸어 중복 삽입을 DB 레벨에서 막거나 상태 기계 기반 조건부 업데이트로 유효한 전이만 허용하거나 처리 이력을 기록해 중복이면 스킵합니다. 고르는 기준은 단순합니다. 삽입이 문제면 유니크 제약이 제일 싸고 확실하고 상태 변경이 문제면 조건부 업데이트, 둘 다 아니면 처리 이력입니다. 어느 쪽이든 같은 메시지가 두 번 와도 결과가 같으면 됩니다.
PART 2 · 통신비동기 운영

컨슈머 lag은 비동기 시스템의
핵심 관측 지표다

  • lag = 발행 속도와 소비 속도의 차이 누적
  • lag 증가 = 처리 지연이 사용자 경험으로 전파되는 전조
  • 파티션 설계·컨슈머 스케일링이 처리량의 상한 결정
비동기 운영에서 봐야 할 지표가 컨슈머 lag입니다. 발행 속도를 소비가 못 따라가면 쌓이는 차이 누적이고 이게 곧 사용자에게 지연으로 도착합니다. 무서운 점은 증상이 조용하다는 겁니다. 에러율은 멀쩡하거든요. 그래서 lag 알람을 따로 걸어야 하고 상시적으로 쌓인다면 화면 마지막 줄처럼 파티션 설계와 컨슈머 스케일링, 즉 처리량의 상한을 다시 볼 시점입니다.

데이터 파트입니다. 한 비즈니스 동작이 여러 서비스의 쓰기를 요구하는 순간 분산 트랜잭션 문제가 시작됩니다. 화면처럼 주문과 결제는 커밋됐는데 재고가 실패하면 이미 커밋된 둘을 어떻게 할 거냐는 문제죠. 교과서 답인 2PC는 코디네이터가 병목이자 단일 장애점이라 실무에서 기피합니다. 현실 대안이 로컬 트랜잭션의 연쇄에 보상을 더한 Saga입니다.
PART 3 · 데이터Saga 패턴

Saga는 롤백 대신
보상 트랜잭션으로 되돌린다

  • 각 단계는 로컬 트랜잭션으로 커밋
  • 중간 실패 시 이미 커밋된 단계를 보상 트랜잭션으로 취소
  • Choreography(이벤트 연쇄) vs Orchestration(중앙 조정자)

Saga는 각 단계를 로컬 트랜잭션으로 커밋하고 중간 실패 시 이미 커밋된 단계를 보상 트랜잭션으로 역순 취소합니다. 여기서 보상이라는 단어가 중요합니다. 롤백이 아닙니다. 결제 취소는 결제를 없었던 일로 만드는 게 아니라 환불이라는 새 사실을 만드는 거고 그 사이 시스템은 이미 다른 상태로 흘러가 있을 수 있습니다. 구현은 이벤트로 이어지는 Choreography와 중앙 조정자가 지휘하는 Orchestration이 있는데, 단계가 서너 개를 넘으면 어디서 멈췄는지 보이는 Orchestration이 운영하기 편했습니다.
PART 3 · 데이터Transactional Outbox

"DB 커밋과 이벤트 발행"의 원자성은
Outbox로 푼다

Saga와 세트로 따라오는 문제가 이겁니다. DB 커밋과 이벤트 발행, 이 둘 사이에 원자성이 없습니다. 커밋 직후 프로세스가 죽으면 이벤트는 영영 안 나가고 알림 서비스는 접수 사실을 모릅니다. Outbox는 화면처럼 이벤트를 비즈니스 데이터와 같은 트랜잭션으로 outbox 테이블에 기록하고 별도 릴레이가 polling이나 CDC로 읽어 브로커에 발행합니다. 릴레이는 실패하면 재발행하니까 발행도 at-least-once가 되고 방금 본 멱등 컨슈머가 다시 전제 조건이 됩니다.

PART 3 · 데이터동시성 제어

분산 락은 최후의 수단 —
설계로 피하는 게 먼저다

  • 우선순위: 유니크 제약 → 조건부 업데이트 → 분산 락
  • Redlock 등 분산 락: 락 만료·경합·시계 오차 등 고려 사항 많음
  • 락을 쓰면 락 실패 시나리오까지 설계에 포함

1st DB 유니크 제약

가장 단순·견고. DB가 원자성을 보장

2nd 조건부 업데이트

상태 조건을 걸어 원자적 전이만 허용

last 분산 락 (Redlock 등)

만료·경합·시계 오차 관리 필요 — 락 자체가 장애 지점이 될 수 있음

동시성 제어는 우선순위가 있습니다. 유니크 제약, 조건부 업데이트, 그다음이 분산 락입니다. 앞의 둘은 DB가 원자성을 보장해 주니까 제일 싸고 견고하고 분산 락은 최후의 수단입니다. Redlock 같은 걸 쓰는 순간 락 만료 시간, 경합, 시계 오차까지 고려 대상이 되고 락 획득 실패 시나리오를 설계하지 않으면 락 자체가 또 다른 장애 지점이 됩니다.

PART 4 · DB 분리왜 마지막 관문인가

DB를 나누지 않으면 MSA는 완성되지 않는다

  • 공유 DB = 스키마가 암묵적 공용 API
  • 인덱스·슬로우 쿼리·커넥션 풀을 전 서비스가 공유하는 성능 결합
  • 서비스 분리의 마지막 관문이자 가장 되돌리기 어려운 작업

스키마 결합

필드 하나 바꾸는 데 전 서비스 협의

성능 결합

한 서비스의 슬로우 쿼리가 전체 레이턴시로

장애 결합

커넥션 풀 고갈·장애가 전 서비스에 전파

마지막 파트, DB 분리입니다. 코드를 잘 나눠도 DB를 공유하면 화면의 세 결합이 남습니다. 스키마가 암묵적 공용 API라 필드 하나 바꾸는 데 전 팀 협의가 필요하고 인덱스와 슬로우 쿼리와 커넥션 풀을 공유하니까 한 서비스의 문제가 전체 성능으로 번집니다. 그래서 DB 분리가 MSA의 마지막 관문인데, 동시에 가장 되돌리기 어려운 작업이라 순서가 중요합니다.

DB 분리는 3단계 —

STEP 1 접근 분리

끊는 결합 — 스키마 결합

STEP 3 물리 분리

비용 대비 효과 따져 선택

끊는 결합 — 성능·장애 결합

2단계까지만으로도 스키마 결합과 접근 결합은 끊긴다 — 3단계는 필수가 아니다
그 순서가 3단계입니다. 1단계 접근 분리는 코드에서 타 도메인 직접 조회를 없애고 소유 도메인 API를 거치게 하는 것, 2단계 schema 분리는 같은 클러스터 안에서 도메인별 DB로 나누는 것, 3단계 물리 분리는 클러스터 자체를 나누는 겁니다. 강조하면 3단계는 필수가 아닙니다. 스키마 결합과 접근 결합은 2단계에서 이미 끊기고 물리 분리는 성능과 장애 격리가 실제로 아플 때 비용 대비 효과를 따져 선택하면 됩니다.

CASE STUDY전환 설계

컷오버는 lag이 0에 수렴해야 전환한다

  • ① full sync 완료 → ② incremental sync로 lag 수렴 확인
  • ③ 애플리케이션 커넥션을 신규 DB로 전환 (컷오버)
  • ④ 이상 시 커넥션 원복 — 롤백 경로 사전 확보
컷오버 절차는 화면 번호 순서입니다. full sync가 끝나면 incremental sync가 따라붙고 여기서 replication lag이 0에 수렴하는지 봅니다. lag이 남았다는 건 아직 타겟에 반영 안 된 쓰기가 있다는 뜻이라 그 상태로 전환하면 그 구간이 유실됩니다. 수렴을 확인한 뒤 애플리케이션 커넥션을 신규 DB로 전환했고 마지막 ④번이 중요합니다. 이상 시 커넥션만 원복하면 되는 롤백 경로를 전환 전에 미리 정의해 뒀습니다.
