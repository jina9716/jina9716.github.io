화면 기준으로 쓰인 QA 테스트 케이스 80건을 서버 API 계층에서 재현해 검증했습니다. 케이스 변환과 하네스 실행은 AI 코딩 에이전트에게 맡기고, 검증 계층 선택과 결함 수정 방향은 직접 정했습니다.

## 배경

개편 대상은 요일별 시간 설정입니다. 기존에는 요일마다 시작 시각과 종료 시각이 한 쌍 있고 휴게 하나가 붙어 있었습니다. 하루를 오전과 오후로 나누거나 저녁 시간대를 따로 여는 경우를 이 구조로는 표현할 수 없었습니다. 그래서 시간을 구간 배열로 저장하고 휴게를 둘까지 두는 구조로 바꿨습니다. 특정 날짜부터 적용되는 변경 예약과 하루짜리 예외 설정도 함께 들어갔습니다.

구 관리자 화면은 여전히 시작 시각과 종료 시각으로 저장 요청을 보내고 새 화면은 구간 배열로 보냅니다. 서버는 두 요청을 모두 받아야 하고 저장된 문서에도 두 포맷이 섞여 있습니다. 이 공존 기간이 개편의 제약이었습니다.

테스트 케이스는 관리자 화면과 사용자 앱 동작 기준으로 80건이 정리되어 있었습니다.

## 검증 계층과 역할 분담

유닛 테스트로는 이번 개편의 핵심을 확인할 수 없습니다. 저장 포맷 판정, 구간 정규화, 컨트롤러의 검증 파이프가 요청 하나에 차례로 걸리고 결과는 저장된 문서의 형태로 남습니다. use-case만 떼어 mock 리포지토리로 테스트하면 요청이 실제로 어떤 문서로 저장되는지는 확인할 수 없습니다. 스테이징에 실제 요청을 보내는 방법은 제외했습니다. 변경 예약과 앱 노출 판정이 현재 시각을 읽어 기준 시각을 고정할 수 없고 케이스마다 데이터를 초기화해야 합니다.

API 계층에서 케이스를 재현하기로 하고 실행을 AI 코딩 에이전트에게 맡겼습니다. 시트를 읽고 케이스마다 전제와 절차를 요청 본문으로 옮기는 것, 하네스를 작성해 실행하는 것, 결과를 케이스별 판정 문서로 정리하는 것까지입니다. 요구사항이 모호한 케이스는 실행 전에 확인을 받도록 했고, 시트의 Preconditions를 그대로 따르는 데서 멈추지 않고 경계값과 예외 경로를 직접 추가해 검증하도록 했습니다.

에이전트에게 넘기지 않은 것은 판단이 갈리는 지점입니다. 검증 계층 선택, 에이전트가 질문한 모호한 케이스의 해석, 화면 규칙을 서버가 막을지, 결함을 어떻게 고칠지입니다.

## 하네스

에이전트가 작성한 하네스는 NestJS 테스트 모듈에 실제 컨트롤러와 use-case, 리포지토리를 그대로 등록하고 supertest로 HTTP 요청을 보내고 응답을 확인하는 구성입니다. 데이터베이스는 `mongodb-memory-server`로 띄운 인메모리 MongoDB이고 MikroORM의 `EntityManager`를 이 인스턴스에 붙여 주입했습니다. Redis, Kafka, 외부 API처럼 호출만 되면 되는 외부 경계는 모든 메서드를 no-op으로 만든 mock으로 두었습니다.

기준 시각은 고정했습니다. `jest.useFakeTimers`로 타이머까지 가짜로 만들면 HTTP 요청 처리와 MongoDB 드라이버가 멈춥니다. 그래서 `Date`만 고정하고 `setTimeout`, `setImmediate`, `nextTick` 같은 타이머 API는 `doNotFake`로 남겼습니다. 인메모리 MongoDB는 단일 노드라 세션 트랜잭션을 열 수 없습니다. 예외 설정 저장이 쓰는 `em.transactional`은 콜백을 바로 실행하고 `flush`하는 것으로 대체했습니다. 같은 적용일로 변경 예약을 두 번 만드는 케이스는 요청이 `EntityManager` 하나를 공유해서 동시 요청으로 재현할 수 없었고 테스트 안에서 유니크 인덱스를 걸어 두 번째 요청이 거부되는 것으로 확인했습니다.

시트 케이스 80건에 시트에 없는 조건을 넣은 확장 점검을 더해 총 133건을 이 구성으로 한 번에 실행합니다.

## 케이스 판정과 확장 점검

화면 기준 케이스는 "블록을 클릭해 종료 시각을 11:47로 바꾸고 저장한다"처럼 조작 단위로 쓰여 있습니다. 서버 입장에서 다시 읽으면 "월요일 구간이 09:00~11:47인 요청이 들어온다"가 되고 기대 결과는 "저장된 문서와 조회 응답의 구간이 09:00~11:47이다"가 됩니다. 이 번역이 되는 케이스는 판정할 수 있고 "저장 버튼이 비활성화된다"처럼 서버에 대응 동작이 없는 케이스는 판정할 수 없습니다. 그래서 Pass와 Fail 외에 N/A를 두었습니다.

케이스 판정은 시트의 Preconditions와 Steps를 글자 그대로 재현한 결과로만 내리고 전제를 벗어난 조건에서 찾은 문제는 확장 점검으로 따로 기록했습니다. 둘을 섞으면 "80건 중 3건 Fail"이 되어 케이스 자체에 문제가 있는 것처럼 읽힙니다. 결함은 케이스가 다루지 않는 조건에 있었습니다. 둘을 한 문서에 나란히 놓는 것이 검증 결과를 정확하게 전달하는 방법이라고 봤습니다.

확장 점검 항목은 에이전트가 선정했고 개편으로 바뀐 지점에 집중됐습니다. 변경 예약과 예외 설정이 같은 날에 걸리면 어느 쪽이 우선인지, 공휴일 칸은 어떻게 적용되는지, 목록 조회가 자정 경계를 어떻게 넘는지를 봤습니다. 구 포맷의 마감 오프셋을 구간으로 옮길 때 값이 어떻게 계산되는지, 구 포맷 문서와 신 포맷 요청이 섞이는 네 가지 조합에서는 어떻게 되는지도 넣었습니다. 화면 기준 케이스는 화면 하나에서 시작하기 때문에 포맷 조합이 포함될 수 없습니다. 결함 세 건은 전부 이 확장 점검에서 나왔습니다.

## 저장 포맷 판정

구 포맷 문서에 새 화면이 구간 배열만 있는 요청을 보내면 여덟 요일 모두 "시간이 없다"는 400 응답이 났습니다. 반대로 신 포맷 문서에 구 화면이 요청을 보내면 204를 내고 아무것도 바꾸지 않았습니다. 두 결함은 같은 판정 함수에서 나왔습니다.

기존 판정은 저장된 문서의 포맷을 먼저 봤습니다. 구 화면은 조회 응답에 들어 있는 구간 배열을 가공하지 않고 저장 요청에 그대로 되돌려 보냅니다. 그 구간은 저장 시점의 구 시각에서 파생한 값이라 사용자가 구 시각을 고쳤어도 옛 값 그대로입니다. 구 시각과 구간을 함께 저장하면 두 표현이 어긋난 문서가 되니 구 포맷 문서에서는 요청의 구간을 버려야 했습니다. 이 논리를 "저장된 문서가 구 포맷이면 구간을 버린다"로 구현한 것이 문제였습니다. 새 화면 요청에는 구 시각이 없으니 구간을 버리면 남는 것이 없었습니다.

바꾼 판정은 요청이 어느 화면에서 왔는지를 요청의 필드로 판별합니다.

- 구 시각 필드가 없다: 새 화면의 신 포맷 저장이다. 저장된 문서가 구 포맷이어도 신 포맷으로 바꿔 저장한다.
- 구 시각 필드만 있다: 구 화면의 편집이다. 구 포맷으로 저장한다.
- 구 시각 필드와 구간이 함께 있다: 구 화면이 조회 응답을 되돌려 보낸 것이다. 구간은 버리고 구 시각을 저장한다. 저장된 문서가 신 포맷이면 구 시각으로 되돌릴 수 없으므로 400으로 거부한다.

두 포맷을 서로 변환해서 한 포맷으로 저장하는 방법은 버렸습니다. 신 포맷은 구간이 여러 개인데 구 포맷은 시작과 종료가 하나라 신에서 구로는 정보가 손실됩니다. 변환은 읽기 쪽 어댑터에만 두고 저장은 변환하지 않기로 했고 변환하지 않으면 되돌릴 수 없는 요청은 거부해야 합니다. 세 번째 경우의 400 거부가 그것이고 이전에는 빠져 있었습니다. 요일마다 따로 판정하는 방법도 버렸습니다. 한 문서 안에 두 포맷이 섞이면 읽기 어댑터가 문서 전체를 건너뛰기 때문에 요일 하나라도 구 포맷이면 여덟 요일을 모두 구 포맷으로 봅니다.

나머지 결함 한 건은 예외 설정 저장이 두 종류 구간 중 한쪽을 필수로 보고 다른 쪽만 있는 요청을 400으로 거부한 것입니다. 주간 설정은 둘 중 하나만 있으면 저장하는 규칙이라 두 저장 경로의 규칙이 어긋나 있었습니다.

## 화면에만 있는 규칙

결함으로 판정한 것은 이 세 건입니다. 판정하지 못한 N/A 40건 중 12건은 서버가 무엇을 저장하는지 확인했지만 기대 결과가 서버에 없는 규칙이었습니다.

- 구간을 29분으로 저장하면 막힌다. 서버는 최소 길이를 검증하지 않고 그대로 저장한다.
- 휴게를 하나만 두면 17:00 기준으로 두 종류 중 하나로 자동 분류된다. 서버는 보낸 필드에 그대로 저장한다.
- 구간을 줄여 휴게가 밖으로 밀리면 휴게가 잘리거나 사라진다. 서버는 휴게를 그대로 둔다.
- 변경 예약은 5건까지만 만들 수 있다. 서버에 개수 제한이 없다.

에이전트는 이 사실들을 N/A로 두고 서버가 실제로 저장한 값만 적었습니다. 결함인지 화면 규칙인지는 판정하지 않았습니다. 기준은 저장 상태의 정합에 영향을 주는가로 잡았습니다. 변경 예약 개수 제한은 화면이 "5건이면 더 못 만든다"를 전제로 동작하므로 서버가 여섯 번째를 받으면 화면이 가정하는 상태와 저장된 상태가 어긋납니다. 이런 규칙은 서버가 막아야 합니다. 최소 길이, 휴게 자동 분류, 휴게 조정은 사용성 규칙이라 서버가 몰라도 데이터가 깨지지 않습니다. 이런 규칙은 화면에 둡니다.

## 결과

| 항목 | 건수 |
|---|---|
| 시트 케이스 | 80 |
| Pass | 40 |
| Fail | 0 |
| N/A | 40 |
| 시트 밖에서 찾은 서버 결함 | 3 |
| 하네스 요청 수 | 133 |
| 배포 후 이슈 | 0 |
| 배포 후 CS 인입 | 0 |

검증은 두 회차로 했습니다. 1차 뒤에 시트 문구가 다듬어지고 수정사항 시트가 추가됐습니다. 2차에서는 에이전트가 시트 변경분을 대조해 판정에 영향을 주는 케이스만 다시 확인했습니다. 1차에서 찾아 고친 결함은 2차 문서에서 뺐습니다.

판정 문서에는 하네스로 보지 못한 것도 함께 남겼습니다. 트랜잭션 롤백(인메모리 단일 노드), 동시 요청(`EntityManager` 공유), 캐시 적중 경로(Redis mock이 항상 미스), 인증과 권한(가드 미적용), 변경 예약 전환 배치의 실행 주기(크론 설정이 저장소 밖), 그리고 배지와 안내 문구 같은 화면 표기입니다. 포맷 조합 네 가지를 1차 회차에 넣지 않은 것도 한계입니다. 두 번째 결함은 테스트 서버에서 화면 저장이 실패한다는 보고가 먼저 왔고 그 뒤에 하네스에서 재현했습니다.

## 결론

에이전트는 문서를 재현하는 일을 정확히 수행했습니다. 80건을 요청과 기대 응답으로 옮기고 하네스를 만들어 실행하는 데 고칠 것이 거의 없었고 시트가 바뀐 2차 회차의 대조도 맡길 수 있었습니다. 다만 시트를 재현한 결과는 Fail 0이었습니다. 결함은 경계값과 예외 경로를 직접 추가하라는 지시에서 나왔습니다. 에이전트는 그 지시를 받고 개편으로 바뀐 지점의 상태 조합을 선정해 넣었습니다. 하네스보다 이 지시가 검증 결과를 정했습니다.

판단은 맡길 수 없었습니다. 서버가 29분짜리 구간을 저장한다는 사실은 에이전트가 정확히 보고했지만 그것을 결함으로 볼지는 정책을 알아야 정할 수 있었습니다. 이 기준은 검증이 끝난 뒤에 정했습니다. 에이전트가 검증하지 않은 것을 스스로 목록으로 남긴 점도 중요했습니다. 트랜잭션 롤백, 동시 요청, 캐시 적중을 보지 않았다고 적어 두었기 때문에, 133건이 통과했다는 결과가 어디까지 확인된 것인지 하네스를 직접 읽지 않고도 알 수 있었습니다.
