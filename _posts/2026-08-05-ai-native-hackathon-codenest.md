2026년 3월 사내 해커톤에서 2인 1팀으로 `CodeNest`를 만들었습니다. Claude Code 사용 지표를 드래곤 육성 게임으로 바꿔 놓은 시연용 프로토타입입니다. 코딩 시간 5시간 안에 알 선택부터 대결, 대시보드까지 시연 흐름이 끝에서 끝까지 동작했습니다. 이 글은 코드가 아니라 AI를 어떻게 썼는지를 중심으로 정리했습니다.

## 1. 배경

6팀이 하루 안에 시연 가능한 제품을 만드는 행사였습니다. 실제 코딩에 쓸 수 있는 시간은 5시간 정도였습니다. 규칙 중 개발 방식에 영향을 준 것은 두 가지였습니다.

- **사전 개발 금지, 기획서까지는 허용** - 레포는 당일 오전에 만들었습니다.
- **발표 때 AI 활용 사례 공유 필수** - 다른 팀이 따라할 수 있게 설명해야 했습니다.

심사 배점도 같은 방향이었습니다. AI 활용 창의성 35%, 완성도 25%, 사례 공유 퀄리티 10%. AI로 빨리 만들었다는 것만으로는 점수가 나오지 않고, 워크플로우 자체를 보여줘야 하는 조건이었습니다.

## 2. 무엇을 만들었나

주제는 자유였습니다. 마침 팀 안에서 AI 도구 사용량과 생산성 지표를 어떻게 볼지 논의하던 시기라, 그 지표를 그대로 게임 재화로 쓰기로 했습니다.

효율 점수를 토큰 사용량 대비 산출물로 잡고, 그 점수가 드래곤의 성장 속도와 기분을 결정합니다. 토큰을 많이 쓰는 것 자체는 감점이 아니고, 쓴 만큼 PR과 커밋이 나왔는지를 봅니다. 효율이 낮으면 드래곤이 굶습니다.

게임 화폐는 로그(Log)로 정했습니다. 개발자에게 로그가 쌓인다는 표현이 익숙하고, 통나무를 모아 둥지를 짓는다는 설정과도 맞습니다.

<img src="/assets/images/codenest-hackathon/metric-to-dragon.svg" alt="사내 Prometheus와 DevLake 지표에서 효율 점수를 계산해 등급·EXP·드래곤 6단계 진화로 이어지는 흐름" />

기능은 Character와 AI Productivity로 나눴습니다.

- **Character** - 알 선택(5속성) → 부화 → 6단계 진화, 둥지 꾸미기(드래그앤드롭), 상점 61개 아이템, 다른 사람 드래곤과 대결
- **AI Productivity** - Overview, 팀별 분석, 리더보드, 상세 지표 4개 뷰

저는 모노레포 기반과 Character 전체를, 팀원은 AI Productivity 대시보드와 지표 수집을 맡았습니다.

기술 스택은 기능 구현에 시간을 쓰기 위해 익숙한 조합으로 정했습니다. Turborepo + pnpm workspace 위에 Next.js 14, Express + TSOA + tsyringe, PostgreSQL 16 + Prisma입니다.

## 3. 사전 준비는 문서까지

사전 개발이 금지라 준비할 수 있는 것은 문서까지였습니다. 그래서 당일에 결정할 일이 남지 않도록 문서 단계에서 최대한 많이 정했습니다.

Claude Code의 brainstorming 기능으로 컨셉을 잡았습니다. 혼자 기획서를 쓰면 드래곤을 키운다는 한 줄에서 더 나가지 않는데, 질문을 계속 받다 보니 재화 획득/소비 밸런스, 등급 하락 시 사용자 반응, 자기 자신과 대결하지 못하게 막는 예외까지 전날에 결정할 수 있었습니다.

전날까지 만든 문서입니다.

1. 올인원 기획서 - 성장/경제/대결/대시보드 규칙, 화면별 내용
2. 모노레포 아키텍처 spec - 패키지 구조, 데이터 모델, API 명세
3. 병렬 개발 계획서 - 다음 장에 나오는 팀 구성과 파일 소유권

## 4. Agent Teams로 병렬 개발

한 세션으로 순차 진행하면 전날 문서에 적어 둔 화면과 API를 5시간 안에 다 채우지 못합니다. 목록을 줄이는 대신 범위를 유지하기로 하고, Claude Code의 Agent Teams로 5개 세션을 동시에 돌렸습니다.

<img src="/assets/images/codenest-hackathon/agent-team-parallel.svg" alt="Phase 0에서 Lead가 공용 파일을 선점하고 Phase 1에서 teammate 4명이 각자 소유한 파일을 병렬로 작업하는 구조" />

같은 병렬화를 subagent로도 할 수 있습니다. 다만 subagent는 세션끼리 직접 대화하지 못해서, 프론트 쪽이 API 응답 형식을 물을 때마다 Lead를 거쳐야 하고 그 왕복이 전부 Lead의 컨텍스트를 씁니다. Agent Teams는 teammate끼리 직접 메시지를 보내고 task 목록도 공유합니다. 5시간 내내 Lead의 컨텍스트를 조율에만 쓰려면 이쪽이어야 했습니다.

병렬 개발에서 실제로 걸리는 것은 파일 충돌입니다. Phase 0은 제가 직접 순차로 처리했습니다. shared 타입과 상수, Prisma 스키마와 시드, JWT와 auth middleware, 그리고 `index.ts`와 `ioc.ts` 골격까지입니다. 여러 teammate가 동시에 수정할 가능성이 있는 파일은 전부 여기에 넣고, Phase 1에서는 수정 금지로 걸었습니다.

Phase 1은 teammate 4명이 각자 소유한 파일만 수정했습니다. `apps/server`와 `apps/web` 사이에는 겹치는 파일이 없으니, 백엔드 두 명은 controller/service 이름 단위로, 프론트 두 명은 page/component 단위로 나눴습니다. 한 명당 task를 5~6개씩 배정하고, 서로 기다려야 하는 자리는 task 의존성으로 걸었습니다. 드래곤 화면은 드래곤 API와 둥지 API가 끝나야 붙고, 상점 화면은 상점 API가 끝나야 붙습니다.

teammate 4명에게는 코딩을 시작하기 전에 계획 승인을 받게 했습니다. 세션이 네 개면 결과물도 네 뭉치로 한꺼번에 들어오는데, 명세를 잘못 읽은 것은 코드가 나온 뒤보다 계획 단계에서 잡는 쪽이 비용이 적습니다.

소유권으로 막을 수 없는 파일이 한 종류 있습니다. 생성 파일입니다. TSOA route는 재생성할 때마다 백엔드 두 명이 같은 파일을 덮어쓰기 때문에, 계획 단계에서 미리 찾아 두고 소유권 대신 실행 순서로 막았습니다.

모델은 Lead만 Opus, teammate 4명은 Sonnet으로 뒀습니다. teammate가 하는 일은 이미 정해진 명세를 코드로 옮기는 것이라 Sonnet으로 충분했고, 예상 토큰 900K를 전부 Opus로 돌릴 이유가 없었습니다.

여기에 typescript-lsp 플러그인을 붙여 뒀습니다. 편집 직후 진단이 돌아서 오타, 미사용 import, 반환 타입 누락은 제가 보기 전에 정리됐습니다. 다섯 세션이 동시에 코드를 만드는 상황이라 사람이 볼 리뷰 분량이 그만큼 줄었습니다.

## 5. 에셋 78장을 같은 스타일로

6단계 진화는 단계마다 에셋이 있어야 시연에서 드러납니다. 5속성 × 6단계면 드래곤만 30장이고, 둥지 테마 9장과 소품 34장, 액세서리 5장을 더하면 78장입니다.

<img src="/assets/images/codenest-hackathon/dragon-evolution-grid.svg" alt="불·물·자연·번개·마법 5속성의 알부터 전설까지 6단계 드래곤 SVG 30장을 격자로 나열한 그림" />
<span class="fig-note">드래곤 에셋을 블로그용으로 다시 그린 그림입니다. 실제 파일은 레포에 있습니다.</span>

에셋을 이미지 생성 모델로 만드는 안을 먼저 목업으로 만들었습니다. 공통 프롬프트 하나에 속성별 문구와 단계별 문구를 얹는 구조로, 드래곤과 둥지 배경, 소품까지 자리마다 생성용 프롬프트를 적었습니다. 등급별 표정과 둥지 배치도 같이 잡았습니다.

<img src="/assets/images/codenest-hackathon/ai-asset-mockup.jpg" alt="공통 프롬프트에 속성별·단계별 문구를 더해 6단계와 5속성, 등급별 표정, 둥지 배경과 소품 자리까지 배치한 이미지 생성 목업" />

이 안은 쓰지 않았습니다. PNG는 도구를 따로 오가야 하고 배경 처리가 남는데, SVG는 코딩 세션 안에서 바로 나오고 나온 뒤에도 코드라서 좌표와 색을 직접 고칠 수 있습니다. 레포에 남은 에셋 78장이 전부 SVG인 것은 그래서입니다.

장수보다 어려운 것은 스타일을 맞추는 일입니다. 30장을 각각 다른 프롬프트로 만들면 선 굵기와 채도가 제각각이라 같은 드래곤이 자란 것으로 보이지 않습니다. 속성과 단계, 등급을 파라미터로 받아 프롬프트를 조립하는 화면을 따로 만들고, 단계가 올라갈 때 더해지는 요소만 조건으로 붙였습니다. 날개는 3단계부터, 왕관은 5단계부터 붙습니다.

## 6. 결과

리더보드에 더미 데이터를 넣으면 시연에서 바로 티가 납니다. 팀원이 수집 스크립트를 작성해 사내 Prometheus에서 Claude Code 사용량 시계열을, DevLake에서 커밋·PR·배포 지표를 CSV로 내보낸 뒤 시드로 변환했습니다.

5시간 동안 이 정도가 남았습니다.

- 커밋 48개, 212개 파일, 25,000줄 남짓
- 페이지 13개, API 엔드포인트 20개 이상
- SVG 에셋 78장, 상점 아이템 61개
- Prisma 테이블 8개

## 7. 결론

세션을 몇 개까지 늘릴 수 있는지는 모델이 정하지 않았습니다. 소유권을 겹치지 않게 나눌 수 있는 파일 단위가 몇 개인지가 정했습니다. Phase 0에서 공용 파일을 먼저 확정해 둔 덕분에 나머지 시간을 병렬로 쓸 수 있었고, 나눌 단위가 더 없는 상태에서 세션만 늘리면 충돌을 정리하는 시간이 따라 늘어납니다.

teammate 4명은 5시간 내내 Sonnet으로 돌았습니다. 명세가 문서에 다 적혀 있는 작업이라 모델 등급이 결과를 좌우하지 않았습니다. Opus를 쓴 자리는 명세를 확정하고 teammate의 계획을 승인하는 쪽이었고, 계획 승인을 코딩 앞단에 건 것도 같은 판단입니다.

평소 업무에서는 세션 다섯 개를 한 번에 돌릴 일이 없습니다. 하루 동안 그 방식을 끝까지 밀어붙여 보고, 어디까지 에이전트에 넘길 수 있고 어디부터 사람이 정해야 하는지 확인할 수 있어서 좋은 경험이었습니다.
