# 도트 펫 스프라이트 후처리 컨텍스트

생성 단계의 지침은 `sprite-context.md` 에 있다. 이 문서는 생성된 격자 한 장을
블로그에 올릴 스프라이트시트로 만드는 절차를 다루며, 실제로 적용한 값을 적는다.

## 전제

나노바나나에서 2×8 격자 **한 장**으로 받았다. 가로 2프레임(A/B) × 세로 8상태가
한 장에 들어 있다. 원본은 `_pet/source-grid.png` 이고 크기는 1024×4128, 셀은 512×516 으로 정확히 균등하게 나뉜다.

생성 결과에는 안티에일리어싱과 팔레트를 벗어난 색이 섞여 있고, 배경 마젠타도
단색이 아니라 잡티가 섞인 면이다.

## 목표 스펙

- 셀 **86×86**, 투명 배경 PNG
- 팔레트 17색 정확히 준수
- 가로 2프레임(A/B) × 세로 8상태 = **172×688**
- 행 순서: idle-greeting, deploy-success, testing, coffee,
  build-failed, refactoring, writing, debugging

### 셀을 64 가 아니라 86 으로 잡은 이유

원본의 도트 한 칸은 6px 이다. 셀이 512px 이므로 그림의 실제 해상도는 한 변 85칸이고,
512px 는 그것을 6배로 부풀려 놓은 상태다. 64칸으로 줄이면 칸의 25%를 버리게 되어
눈동자 흰 하이라이트와 귀 안쪽 그림자(`#C97F8A`)처럼 한 칸짜리 요소가 사라진다.
실제로 64칸으로 뽑았을 때는 17색 중 16색만 쓰였고, 그것을 화면에서 2배로 늘리니
뭉갠 자국이 그대로 커져 보였다.

86칸은 원본 도트와 거의 1:1 이라 화면에서 확대할 필요가 없다. 17색이 전부 쓰인다.

## 도구

ImageMagick, Pillow, pngquant, oxipng 가 모두 설치되어 있지 않아서 전 과정을
파이썬 표준 라이브러리로 구현했다. 외부 의존성은 없다.

- `_pet/pngio.py` : PNG 디코더와 인코더
- `_pet/build_sheet.py` : 0단계부터 8단계까지 전부

실행 방법은 다음과 같다.

    python3 _pet/build_sheet.py [--size N]

`--size` 로 셀 크기를 바꿀 수 있다. 기본값은 86 이다.

## 파일 명명 규칙

    _pet/source-grid.png                                     원본 격자
    _pet/aligned/<state>_<frame>.png                         정렬 완료 프레임 16장
    assets/pet/pet-sheet.png                                 최종 시트

    state = idle-greeting | deploy-success | testing | coffee |
            build-failed | refactoring | writing | debugging
    frame = a | b

`raw/` 와 `clean/` 은 따로 만들지 않는다. 한 스크립트가 한 번에 처리하므로
중간 파일을 디스크에 남길 이유가 없다. 눈으로 확인할 것은 `_pet/aligned/` 에 있다.

## 0단계: 격자 분할

셀은 512×516 으로 균등하게 나뉜다. 다만 **셀 경계를 그대로 쓰지는 않는다.**
셀마다 내용의 경계 상자를 다시 잡고, 그 상자를 기준으로 재배치한다.
캐릭터가 셀 안 어디에 그려졌든 결과가 같은 자리에 오게 만들기 위해서다.

### 원본 결함 보정

deploy-success 의 B 프레임은 꼬리를 오른쪽으로 옮겨 그리면서 왼쪽 꼬리를 지우지
않아 꼬리가 둘로 보인다. 생성 단계의 결함이므로 후처리에서 그 자리를 배경색으로
덮는다. `REPAIRS` 에 상태와 프레임 번호, 셀 안의 사각형으로 적는다.

꼬리가 몸통 외곽선에 붙는 밑동까지 걷어내야 해서 사각형 하나로는 되지 않는다.
아래로 갈수록 좁아지는 모양을 사각형 세 개로 따라간다. 더 넓게 잡으면 엉덩이
실루엣이 잘리고, 좁게 잡으면 밑동이 남는다.

경계를 정할 때 주의할 점이 하나 있다. B 프레임은 6단계 정렬에서 원본을 8px 쯤
오른쪽으로 옮겨 다시 샘플링한다. 그래서 A 프레임 좌표로 잰 자리보다 오른쪽
경계를 그만큼 넉넉히 잡아야 한다. 이것을 놓치면 외곽선 바깥에 크림색 픽셀이
두어 개 남는다.

## 1단계: 투명화

배경이 `#FF00FF` 하나가 아니라 잡티가 섞인 마젠타 면이다. 색 하나를 지우는 방식
대신 범위로 판정한다.

    빨강 > 150, 파랑 > 150, 빨강 - 초록 > 60, 파랑 - 초록 > 55, |빨강 - 파랑| < 70

귀 안쪽 분홍은 파랑이 초록보다 크게 높지 않아 이 조건에 걸리지 않는다.

검수는 불투명 픽셀의 비율로 한다. **0.385** 가 나왔고, 0.15 에서 0.5 사이면 정상이다.
1에 가까우면 투명화가 안 된 것이고, 0에 가까우면 캐릭터까지 지워진 것이다.

## 2단계: 본체 검출

셀마다 불투명 픽셀의 연결 성분을 8방향으로 구하고, 가장 큰 성분을 본체로 본다.
머리 위 체크나 등 뒤 불꽃 같은 액센트는 본체와 떨어진 별개의 성분이지만,
셀 전체를 함께 변환하므로 본체와의 상대 위치가 유지된다.

## 3단계: 공통 배율

**프레임마다 본체 상자를 새로 재지 않는다.** 행마다 A 프레임에서 기준점을 한 번 뽑아
A 와 B 에 똑같이 적용한다.

프레임마다 재면 귀를 세우거나 앞발을 벌린 포즈에서 상자가 커져서 개가 커졌다
작아졌다 한다. build-failed 가 그 예인데, A 의 본체 높이는 371 이고 B 는 469 다.
포즈가 달라서 생긴 차이인데 이것을 크기 차이로 읽으면 재생할 때 그대로 떨림이 된다.

배율은 16셀의 내용이 전부 캔버스 안에 들어가는 가장 큰 값으로 정한다. 머리 위
체크와 등 뒤 불꽃까지 포함한 상자로 따지고, 가장자리에 1px 을 남긴다.
결과는 **0.1646** 이고, 출력 1픽셀이 원본 6.1px 에 해당한다. 본체 높이 453px 이
75px 이 된다.

## 4단계: 64×64 재배치

본체의 좌우 중심을 x=43 에, 본체의 최하단을 y=81 에 맞춘다.

여기에 보정이 하나 더 들어간다. 기준점은 원본 좌표에서 잡지만, 줄일 때 마지막 줄이
살아남는지는 그 줄에 원본 픽셀이 몇 개 걸리느냐에 달려 있어서 행마다 1px 씩 갈린다.
그래서 A 프레임을 한 번 뽑아 보고 발바닥 줄의 최빈값에 맞춰 기준점을 되돌린다.
최빈값은 y=80 이고, debugging 행 하나가 보정 대상이었다.

보정 뒤 **A 프레임 8종의 발바닥이 전부 y=80** 에 놓인다. B 프레임 중 둘
(idle-greeting 79, build-failed 81)은 일부러 어긋나 있다. 원본에서 개가 위아래로
움직이는 부분이라 맞추면 애니메이션이 죽는다.

## 5단계: 팔레트 양자화

출력 픽셀 하나가 덮는 원본 영역에서 **가장 많이 나온 색**을 고르고, 그 색을 17색 중
가장 가까운 색으로 바꾼다.

점 하나만 찍어 오는 방식은 쓰지 않는다. 그 점이 잡티일 때 눈과 하이라이트가
통째로 사라지기 때문이다. 영역 최빈값은 색을 섞지 않으므로 원본에 없던 색이
생기지 않고, 디더링도 발생하지 않는다. 배경이 영역의 절반을 넘으면 투명으로 둔다.

검수 결과는 다음과 같다.

- 쓰인 색 **17/17**, 팔레트 밖의 색 없음
- 알파 값은 0 과 255 뿐이며 중간값이 없다. 안티에일리어싱이 남지 않았다는 뜻이다
- 프레임 하나가 쓰는 색은 최대 14개다

## 6단계: A/B 프레임 정렬

**B 프레임이 셀 안에서 밀려 그려져 있다.** 8행 중 5행에서 가로로 같은 방향의
어긋남이 나왔다.

출력 한 칸 단위로 대강 찾은 뒤, **고른 양만큼 원본 좌표에서 다시 뽑는다.**
이미 줄여 놓은 이미지를 옮기면 뭉갠 픽셀을 한 번 더 옮기는 셈이라 경계가 더 나빠진다.

가로는 **0.25칸까지** 좁혀서 본다. 0.5칸 간격으로만 찾았을 때 refactoring 행의
실루엣이 1px 어긋난 채로 남았다. 전체 픽셀 차이로는 잡히지 않았는데, 렌치를 든
앞발이 크게 움직여서 그쪽이 지표를 먹었기 때문이다. 불꽃을 빼고 A 와 B 를 겹쳐 보면
오른쪽 실루엣에 A 만, 왼쪽에 B 만 한 줄씩 남는 형태로 드러났다.

    행               정렬 전 -> 정렬 후   옮긴 양
    idle-greeting      1598  ->  1374    dx-1.00 dy-0.50
    deploy-success     1183  ->   720    dx-1.25
    testing            1136  ->   237    dx-1.25
    coffee             1570  ->  1267    dx-1.25
    build-failed       1871  ->  1822    dx-1.25 dy-0.50
    refactoring        1124  ->   677    dx-1.25
    writing            1298  ->  1283    dx+0.25 dy-0.50
    debugging          2468  ->  2014    dx-3.50 dy-0.50

**남은 차이는 평행이동으로 줄지 않는다.** build-failed 와 debugging 은 A 와 B 가
사실상 다른 포즈로 그려져 있다. build-failed 의 A 는 귀를 접고 얼굴을 가린 자세이고
B 는 귀를 세우고 고개를 튼 자세다. 원래 계획대로라면 이 두 행은 B 생성을 포기하고
A 를 픽셀 시프트해서 만드는 쪽이 맞지만, 어떻게 움직일지는 아직 정하지 않았다.

## 7단계: 시트 병합

행 순서를 지켜서 가로로 A, B 를 붙이고 세로로 8행을 쌓는다. 결과는 172×688 이다.

## 8단계: 최적화

pngquant 와 oxipng 가 없어서 **인덱스 PNG**(컬러타입 3)로 직접 인코딩한다.
색이 17개뿐이므로 픽셀당 4바이트 대신 1바이트면 되고, 손실은 없다. 인덱스 0을
투명으로 두고 tRNS 로 알파를 준다. RGBA 로 쓰면 10.0KB 인 것이 **10.3KB** 가 된다.

## 9단계: 블로그 적용

시트는 `/assets/pet/pet-sheet.png` 에 있다. 표시 배율은 CSS 변수 하나로 정하고,
`width` 와 `background-size` 와 프레임 이동값이 모두 거기에서 계산된다.
소수 배율을 쓰면 프레임 경계가 픽셀에 떨어지지 않아 세로줄이 생기므로 정수배만 쓴다.

    .pet__sprite {
      --pet-scale: 1;
      width: calc(86px * var(--pet-scale));
      height: calc(86px * var(--pet-scale));
      background-image: url("/assets/pet/pet-sheet.png");
      background-repeat: no-repeat;
      background-size: calc(172px * var(--pet-scale)) calc(688px * var(--pet-scale));
      image-rendering: pixelated;
      animation: petFrames var(--pet-dur, 800ms) steps(2) infinite;
    }
    @keyframes petFrames {
      from { background-position-x: 0; }
      to   { background-position-x: calc(-172px * var(--pet-scale)); }
    }

상태별로 `background-position-y` 와 속도를 붙인다.

    상태              행   background-position-y          속도
    idle-greeting     0    calc(-86px * scale * 0)      1000ms
    deploy-success    1    calc(-86px * scale * 1)       500ms
    testing           2    calc(-86px * scale * 2)       700ms
    coffee            3    calc(-86px * scale * 3)      1200ms
    build-failed      4    calc(-86px * scale * 4)       500ms
    refactoring       5    calc(-86px * scale * 5)       400ms
    writing           6    calc(-86px * scale * 6)       600ms
    debugging         7    calc(-86px * scale * 7)       700ms

build-failed 는 원래 300ms 로 잡았는데 실제로 보니 나머지와 견주어 지나치게 빨라서
500ms 로 올렸다.

`steps(2)` 에 시트 두 칸 폭까지 적는 것이 요점이다. steps 는 마지막 값에 닿지
않으므로 0 과 한 칸, 두 자리만 재생된다.

동작 최소화를 켠 사용자에게는 `_sass/_base.scss` 의 전역 규칙이 애니메이션을 멈춰서
A 프레임에 선다.

### 상태 문구

클릭하면 다음 순서로 넘어간다. 문구는 `assets/js/site.js` 에 있다.

    deploy-success    배포 성공
    testing           테스트 중

    build-failed      빌드 실패

    debugging         버그 추적 중
